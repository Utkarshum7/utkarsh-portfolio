## Summary

Keyword matching is easy to game: a résumé can list "LangChain" without ever having built anything with it. Asking an LLM for a score is hard to audit: you can't explain why one candidate got a slightly higher number than another. I split the job. **The LLM does the one thing a regex can't**, reading a project description and classifying how deep it really is, and **plain Python does everything else**: the eligibility gate, every point of the score, penalties, and the ranking. <Claim id="ars.what" sidenote>Every score is computed in Python.</Claim>

## The split

| Deterministic (Python) | Semantic (LLM) |
|---|---|
| File discovery, duplicate detection (SHA-256) | Reading project descriptions |
| Text extraction and normalisation | Classifying each project: real implementation, thin wrapper, tutorial, or skill mention |
| Name, email, GitHub and skills extraction | Summarising strengths and concerns |
| The hard eligibility gate | — |
| **All scoring and ranking** | — |

The LLM is called once per candidate, **only for candidates who already passed the <Claim id="ars.eligibility">eligibility gate</Claim>**, and its answer must validate against a Pydantic schema before it is used. Rejected candidates stay in the output with explicit reasons; nobody silently disappears.

## Scoring you can trace

{/* sourced: ars.rubric */}
| Category | Points |
|---|---:|
| AI, agentic and RAG project depth | 40 |
| Python and backend engineering | 30 |
| Cloud, deployment, full-stack | 15 |
| GitHub activity | 10 |
| Engineering depth (tests, concurrency, queues, containers) | 5 |

<SourceLine id="ars.rubric" />

{/* sourced: ars.rubric */}
**Decision: shallow projects get the same base points, then a visible penalty.** A thin wrapper around an API is still an AI project, so it earns the base points, and then a separately recorded deduction (−10 for a thin wrapper, −8 for a tutorial-style project). The judgement shows up in the output as a named penalty instead of hiding inside a lower score.

## The hard part: one failure costs one candidate, not the batch

A batch job that calls two external services per candidate will hit failures: unreadable PDFs, truncated LLM JSON, timeouts, GitHub rate limits. Every stage that can fail writes a status onto that candidate's record instead of raising.

{/* sourced: ars.rubric */}
- **LLM call fails or returns invalid JSON:** <Claim id="ars.fallback">the candidate is scored with a deterministic fallback</Claim>, and the AI-depth category is capped at 24 of its 40 points because depth can't be judged from keywords alone.
- **GitHub API:** rate-limit aware, with an <Claim id="ars.github">in-run cache</Claim> so the same profile is never fetched twice in one run.
- **Tests** mock every external call and cover the failure paths.

**Recovering hidden links.** Many résumé templates show "GitHub" as an icon with the URL stored only in the PDF's link annotations. Plain text extraction never sees it, so the pipeline reads PDF link annotations separately.

## Results

<Claim id="ars.run50" sidenote>In one run over 50 real PDF résumés, all 50 parsed and 33 passed the eligibility gate. Of the 33 LLM calls, 30 succeeded; the 3 failures (two truncated JSON responses, one timeout) were each confined to their own candidate, who was still scored by the deterministic fallback and ranked.</Claim> The résumés and outputs aren't published, because they contain personal information. These are totals from one run, not an accuracy measurement: there's no labelled ranking to compare against.

## Limitations and fairness

Automated screening affects people, so its limits belong on the page:

{/* sourced: ars.limits */}
- **Weights are not calibrated.** There is no labelled ranking set; the scoring weights and penalties are judgement, not fitted.
- **Keyword-based eligibility** can miss candidates who describe their work in unusual words, and broad terms can match non-AI work.
- **Parsing limits:** image-only PDFs aren't OCR'd; two-column headers can break name extraction; DOCX hyperlinks aren't read.
- **Only the first 6,000 characters** of each résumé go to the LLM, and long responses can be truncated.
- **Personal data** in the outputs has no access control; it's a local batch tool, not a service.
- It's a shortlisting aid for a human reviewer, not a decision-maker. Every rejection carries a stated reason so a person can overrule it.

<SourceLine id="ars.limits" />

## Lessons

- Put the model where judgement is needed and nowhere else; the rest should be code you can test.
- Make the model's influence visible (named penalties, per-category scores) so a human can disagree with it specifically.
- Design batch pipelines around partial failure from the start.
